# 第三轮优化升级计划：从 HTML 微调工具走向 HTML PPT 编辑器

## 1. 背景判断

当前项目已经完成了从 MVP 到第二轮编辑体验增强的主要演进：

- 可以导入单个 HTML 或本地文件夹项目
- 可以在 iframe 画布中预览、选中元素、编辑文本和常见样式
- 可以将改动写回源码并导出 HTML 或 ZIP
- 已经具备折叠源码、画布比例、缩放、浮动工具条、撤销/重做、草稿恢复、图片替换和图片焦点拖动

这说明产品已经不是普通的 HTML 预览工具，而是进入了“轻量可视化编辑器”的阶段。第三轮不应该继续零散堆功能，而应该把产品、交互和代码结构一起升级。

## 2. 当前核心问题

### 2.1 编辑模型偏脆

当前源码写回主要依赖：

- `buildSourceMap`
- `findElementSourceRange`
- `syncElementToSource`
- 元素 index path
- opening tag / outerHTML 字符串匹配

这套方案对文本、属性、inline style 微调是有效的，但面对以下能力会变得脆弱：

- 自由拖拽移动
- 边角 resize
- 多选编辑
- 对齐和分布
- CSS 规则级编辑
- slide 复制、删除、排序
- 动态 DOM 或复杂模板结构

第三轮必须先加强“选中对象到源码位置”的稳定性，再逐步打开复杂编辑能力。

### 2.2 主应用文件过大

`app.js` 同时承担了：

- DOM 查询和事件绑定
- 应用状态
- 源码编辑
- 预览渲染
- 选中态
- inspector 表单
- 浮动工具条
- 图片替换
- 图片焦点拖动
- 历史记录
- 草稿
- 导出

继续往这里加功能会让修改风险快速上升。第三轮需要先拆清楚边界，后续功能才能稳。

### 2.3 iframe bridge 膨胀风险高

`src/previewBridge.js` 现在已经负责 hover、selected、contenteditable、图片焦点拖动、拖放替换等逻辑。

本地历史里曾经出现过一次“可视化拖拽缩放与多选图层编辑”的大提交，随后被 revert。那次改动大量集中在 preview bridge 侧，说明直接把复杂视觉编辑继续塞进注入脚本，容易把桥接层变成难维护的巨型脚本字符串。

第三轮如果重做拖拽、多选和 resize，应该拆出独立的视觉编辑协议和数据结构，而不是原样恢复被 revert 的实现。

### 2.4 产品心智还不够 PPT/设计工具

当前界面已经有画布感，但用户仍然主要围绕“选中一个 DOM 元素后改属性”工作。

真正面向 HTML PPT 的工作流还缺少：

- slide 列表
- 当前页面缩略图
- 图层/对象列表
- 锁定、隐藏、命名
- 多选
- 对齐、分布、等宽、等高
- 页面复制、删除、排序
- 演示模式
- 图片/PDF 导出

第三轮应先把对象、页面、图层这三种心智建立起来。

### 2.5 性能验证不足

当前检查脚本能覆盖语法、静态片段、资源导入、ZIP 和源码映射的局部逻辑，但缺少真实浏览器级验收：

- 大 HTML 渲染是否卡顿
- 大图片/多资源项目是否能稳定导入
- 浮动工具条是否遮挡内容
- 移动端布局是否可用
- 导出的 HTML/ZIP 是否能真实打开
- iframe 里的拖放、contenteditable、焦点拖动是否符合预期

第三轮需要补上浏览器验收和更接近真实项目的样例集。

## 3. 第三轮目标

第三轮目标不是一次性做完所有高级能力，而是把项目升级成一个能长期迭代的 HTML PPT 编辑器底座。

核心目标：

1. 重构应用边界，让主流程更清楚
2. 强化源码映射和编辑写回能力
3. 把 UI 从“三栏属性编辑器”升级为“画布 + 图层 + 属性 + 页面”的编辑器
4. 为拖拽、resize、多选、slide 管理建立可靠基础
5. 建立真实运行验收，避免只靠静态检查

## 4. 分阶段路线

### 阶段一：编辑器地基重构

目标：不改变用户可见功能，先降低后续升级风险。

计划：

- 拆分 `app.js` 中的项目状态、选中状态、编辑动作、渲染会话和导出逻辑
- 建立统一的 `projectState`，包含 source、entryPath、assetUrls、projectFiles、sourceLabel
- 建立统一的 `selectionState`，包含 editorId、sourceRange、elementPath、selectionLabel
- 将 inspector 和 floating toolbar 的样式写入统一编辑动作层
- 梳理 preview bridge 事件协议，形成固定消息类型
- 给关键动作补单元测试：文本写回、属性写回、样式写回、图片引用替换、焦点样式写回、导出清理

验收：

- 现有 `npm run check` 通过
- 单文件导入、文件夹导入、文本编辑、样式编辑、图片替换、HTML/ZIP 导出行为不退化
- `app.js` 职责明显变薄

### 阶段二：编辑器工作区升级

目标：让界面更像可重复工作的设计/PPT 编辑器。

计划：

- 增加左侧工作区模式：源码 / 图层 / 页面
- 图层面板显示当前画布内主要可编辑元素
- 页面面板识别 `.slide`、`section` 或可配置页面容器
- inspector 改成更轻的对象属性面板，减少长表单压迫感
- 浮动工具条保留高频动作，低频动作下沉到右侧
- 增加对象锁定、隐藏的 UI 协议，先做状态展示和跳过选择，再考虑源码持久化
- 增加快捷键提示逻辑，但不在页面里铺说明文字

验收：

- 用户能通过图层列表选择对象
- 用户能通过页面列表切换主要 slide 区域
- 右侧属性面板更短、更聚焦
- 画布区域仍是视觉中心

### 阶段三：可视化编辑能力重做

目标：重新实现拖拽、resize、多选，而不是恢复被 revert 的大提交。

计划：

- 新建独立 `visualEditing` 模块，负责坐标、边界框、变换策略和批量选择
- preview bridge 只发出 pointer 事件和元素几何信息，不直接决定复杂编辑行为
- 主应用决定写回策略：优先 inline style，必要时提示无法安全写回
- 先支持 absolute/fixed/transform 明确的元素拖动
- 对 flex/grid 普通流元素优先提供 margin/spacing 微调，不做误导性的自由拖拽
- resize 先支持图片、卡片、绝对定位元素
- 多选先支持对齐、分布、复制样式，不急着批量源码结构修改

验收：

- 拖拽不会破坏普通流式布局
- resize 不会改变未选中元素
- 多选操作可撤销
- 被 revert 的历史实现仅作为参考，不直接恢复

### 阶段四：HTML PPT 工作流

目标：把工具从“编辑 HTML 元素”升级为“编辑 HTML PPT”。

计划：

- slide 自动识别：
  - `.slide`
  - `[data-slide]`
  - `section`
  - 全屏页面块
- slide 缩略图
- slide 复制、删除、排序
- 当前 slide 聚焦编辑
- 演示模式
- 导出图片
- 导出 PDF
- 保留单文件 HTML 和项目 ZIP 双导出

验收：

- 典型 HTML PPT 能被识别为多页
- 可以完成页面级调整和导出
- 不破坏普通单页作品编辑

### 阶段五：性能和质量体系

目标：让项目能处理真实作品，而不是只跑轻量示例。

计划：

- 建立真实样例目录，覆盖单页、HTML PPT、多图片项目、外部 CSS 项目
- 增加浏览器验收脚本
- 验证不同视口下文字和工具条不重叠
- 验证导出文件可独立打开
- 大资源导入时展示进度或状态
- source map 做增量或缓存优化
- iframe 渲染做分层 debounce

验收：

- 静态检查、单元测试、浏览器验收都通过
- 大文件场景有明确反馈
- 出错时给用户可理解的中文状态

## 5. UI 升级方向

第三轮 UI 不做营销页，不改变产品第一屏就是工具本体的原则。

布局建议：

```text
--------------------------------------------------+
| 顶部：项目、导入、导出、撤销、重做、画布模式      |
+----------+-------------------------+-------------+
| 左侧     | 中央画布                 | 右侧属性     |
| 页面/图层 | slide viewport           | 对象属性     |
| 源码     | 浮动对象工具条            | 样式/资源     |
+----------+-------------------------+-------------+
```

关键原则：

- 画布始终是视觉中心
- 源码是高级入口，不再占主要心智
- 高频动作靠近选中对象
- 低频动作进入右侧属性或顶部菜单
- 页面、图层、对象三种导航要清楚
- 按钮尽量使用符号、图标或短标签，避免工具条文字拥挤

## 6. 技术边界

第三轮默认继续保持轻量静态架构，不立即引入 React、Vite、Monaco。

可以考虑引入依赖的条件：

- 源码编辑需要真正语法高亮和定位，再评估 Monaco
- CSS 规则编辑需要可靠解析，再评估 PostCSS 或轻量 CSS parser
- HTML 写回继续遇到结构性风险，再评估 parse5
- 浏览器验收稳定后，再考虑 Playwright

在此之前，优先用清晰模块和测试把当前原生实现整理稳。

## 7. 第一阶段任务清单

建议下一步从以下任务开始：

1. 新建 `src/projectState.js`，收束项目文件、资源、入口路径和标签
2. 新建 `src/selectionState.js`，收束选中对象、源码范围、路径和尺寸
3. 新建 `src/editorActions.js`，统一文本、属性、样式、图片焦点和图片替换写回
4. 新建 `src/previewProtocol.js`，定义 iframe 与主应用之间的消息类型
5. 将 `app.js` 中对应逻辑迁移到这些模块，保持 UI 不变
6. 扩展测试，确保迁移前后行为一致
7. 再开始 UI 的页面/图层侧栏

## 8. 不建议立刻做的事

第三轮初期不建议直接做：

- 直接恢复 `codex/visual-element-editing` 的拖拽/多选实现
- 一口气引入 React、Monaco、Vite 后再重写全项目
- 先做复杂自由拖拽，再补源码写回模型
- 把所有 CSS 规则编辑都写成 inline style 的简单按钮
- 在没有真实浏览器验收前宣称视觉编辑稳定

这些都容易让项目快速变大，但质量没有同步上来。

## 9. 成功标准

第三轮完成后，产品应该达到：

- 仍然可以轻量本地运行
- 普通用户主要在画布、图层、页面和属性中完成编辑
- 开发者仍然可以展开源码精修
- 文本、样式、图片、页面级编辑有稳定撤销和导出
- 高级视觉编辑不会破坏用户源码
- 后续接入 AI 局部编辑、模板库、导出 PDF 都有清晰落点
